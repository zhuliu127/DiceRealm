二、陷阱复盘（这是本期最重要的产出）
----------------------------------------------------------------
【现象】
第一次 `flutter build apk --release` 打印
    √ Built build\app\outputs\flutter-apk\app-release.apk (32.8MB)
构建"成功"，但解包发现：
    · 没有 lib/…/libapp.so
    · 没有 kernel_blob.bin / vm_snapshot / isolate_snapshot
    · 72 个文件里**完全没有 Dart 代码**
⇒ 这个包装到手机上必定白屏。而工具链全程没有报一个错。

【为什么之前一直没暴露】
P4 / P5 全部 1305 组测试都是 `flutter test`（Dart VM 模式），
走的是 kernel 解释执行，**根本不经过 AOT 编译**。
AOT（gen_snapshot → libapp.so）只在 `build` 时发生。
所以测试再全绿，也不能证明包是好的。

【根因（两层）】

① 增量构建的失效判断错位（真正原因）
   `build` 是指向 `D:\dev\dice-build` 的 junction。
   Flutter 的增量缓存按 **C 盘路径** 判断输出是否最新，
   而实际文件在 D 盘 —— 时间戳/存在性判断出现偏差，
   于是 verbose 日志出现：
       Skipping target: kernel_snapshot_program
       Skipping target: android_aot_release_android-arm
       Skipping target: android_aot_release_android-arm64
       Skipping target: android_aot_release_android-x64
   但下游照常跑：
       aot_android_asset_bundle: Complete
       android_aot_bundle_release_*: Complete
   ⇒ 打包阶段拿不到 app.so，**静默完成**，产出无 AOT 的包。

② native assets 与 test/build 的死锁（次生原因，也很关键）
   path_provider 的两个平台实现把 native assets 拖了进来：
       path_provider_android    → jni + jni_flutter
       path_provider_foundation → objective_c
   objective_c 强制要求 dart assets：
       · enable-native-assets = true  → `flutter test` 正常
       · enable-native-assets = false → `flutter test` 直接拒绝：
         "Package(s) objective_c require the dart assets feature to be enabled."
   所以不能简单地"永久关掉 native assets"。

【解法（已固化为 tool/build_apk.sh）】
   出包期间临时关 native assets（规避 ②），
   出完立刻恢复（否则测试跑不了），
   并且**强制校验 libapp.so 存在**（兜住 ①，防止再次静默产出坏包）。

   脚本 = 关 → build → 校验 libapp.so → 恢复 config（trap EXIT 保证异常也恢复）

【实测对比】
   坏的：32.8MB，无 libapp.so
   好的：56.9MB，三 ABI 各带 libapp.so（+24MB 正是 AOT 代码体积）
   ⇒ **体积差 24MB 是最直观的健康信号：APK 小于 ~50MB 基本可以判定是坏包。**

----------------------------------------------------------------
三、防复发规则（写给以后的自己）
----------------------------------------------------------------
1. **出包只用 `bash tool/build_apk.sh`**，不要裸跑 `flutter build apk`
2. 拿到任何 APK，先 `unzip -l <apk> | grep libapp.so` —— 三行都有才算好包
3. APK 体积 < 50MB ⇒ 直接判为坏包，别浪费时间安装
4. **`flutter test` 全绿 ≠ 包能用**。测试走 VM 不走 AOT，这是两套链路。
   每期收尾必须真出一次包并校验产物，否则问题会一直藏到用户手上。
5. 若脚本报「缺 libapp.so」，说明缓存又串了：
   删 `.dart_tool/flutter_build` 与 `build/app/intermediates/flutter` 后重跑
   （注意：删这两个目录时本机安全策略会因文件数 >50 拦一次，需分批或手动确认；
     **绝不要 `flutter clean`** —— 它会连 build junction 一起删掉）
