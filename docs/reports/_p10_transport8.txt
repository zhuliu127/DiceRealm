■ 问题 1 · 大厅预览角色显示全部信息
  用户原话：大厅里点成员预览，只显示很少的信息，要看全部。
  真因：大厅预览走的是精简摘要（只给昵称 / 角色 / 准备态），没接完整角色卡视图；
        卡片在权威端是有全量数据的，只是 UI 没给入口。
  改动：lib/ui/room/room_lobby_page.dart（40,787 B）
        · 成员行接「查看完整卡」入口 → showCharViewSheet（与游戏内同一弹层，
          同一份数据，所以属性 / 技能 / 背景 / 装备 / 状态全部可见）；
        · 只读：弹层内无任何写回按钮（P4 口径：预览不改权威态）。
  证据：test/p10_t6_room_fixes_test.dart group 1（成员详情 → CharViewKeys.root，
        「测试信念 / 测试经历（1925）/ 测试资产说明 / 教育进步检定」逐项可读；
        未绑卡时给「未绑卡」且不弹只读卡）。
  交叉验证：test/room_lobby_page 相关既有用例全绿（全量 2106 内）。

■ 问题 2 · 潜在疯狂「后台判定」（详见第三节，结论：系统派生状态，不改 UI）
  结论：**不是缺陷，不需要改 UI**。潜在疯狂是 domain 的派生精神态，由「不定疯狂
        的症状随轮次消退」这条规则自动产生；UI 只负责显示与提供治愈入口。
        链路已核实（见第三节）。

■ 问题 3 · 战技按钮「点了没反应」
  用户原话：点战技没有任何可见反馈。
  真因：旧实现 `hostAction('combat.roll')` 发的是**空参数**：
        · 非 KP 走 domain `diceDirect`（只有 expr/label/skill 三个 null）；
        · KP 走 `diceRoll`（`p['result']` 为空 → 只落一条 total=null 的空 DICE 记录）。
        两条路径都没有可看见的骰点/标签，用户感知就是「点了没反应」。
  改动：lib/ui/room/widgets/gp_dice_bar.dart
        `RoomKeys.action('combat.roll')` 的 onTap 改为
        `sendIntent(INTENT.DICE {expr:'1D100', label:'战技', skill:'战技',
         direct:true, bonus, penalty, secret?})` —— 权威端 `diceDirect` 用规则服务
        复算并 PUBLIC 广播骰点，KP 与玩家两条路径都有可见反馈。
        `enabled` 仍恒等 `gate.can('combat.roll')`（T-30 不漂移），key 不变。
  证据：p10_t6_room_fixes_test 3A[host] / 3A[p1]：发出 intent 的 p 逐字段断言
        （direct=true / expr=1D100 / label=战技 / skill=战技），且 host.state['dice']
        真的多出一条 total 非 null、label=战技 的公共骰；3B 旁观者结构上没有该按钮。
        反向证伪 F2（去掉 direct:true → 该用例红 → 恢复 → 绿）。

■ 问题 4 · 对抗按钮「提示没有对象」
  用户原话：点对抗弹「甲方无效：未指定对抗方类型」。
  真因：旧实现 `hostAction('check.opposed')` 空参数，domain `checkOpposed` 第一步
        `resolveActorSkill(p['aSeat'])` 拿不到座位，直接回「甲方无效」。
        正确入口是已有的能选双方 / 通用 / 攻击 / 武器对抗的弹层。
  改动：同文件，`RoomKeys.action('check.opposed')` 的 onTap 改为
        `showOpposedSheet<void>(context)`；不再发空 action。key / enabled / hint 不变。
  证据：p10_t6_room_fixes_test 4A：点对抗 → OpposedSheetKeys.root 出现，
        `f.lastSent(action:'check.opposed')` 为 null（证明不再发空 action）；
        4B 玩家/旁观结构上没有该按钮（POLICY = [kp]）。

■ 问题 5 · 推送要求要「屏幕正中弹窗」且能直接操作

三、问题 2「潜在疯狂后台判定」的明确结论
================================================================================
结论：**这是系统派生状态，不是缺陷，不改 UI。**

1) 定义与产生条件（lib/domain/madness_state.dart 文件头 13–20 行，原文口径）：
   · 精神状态的取值只有：正常 / 临时疯狂 / 不定疯狂 / 潜在疯狂 / 永久疯狂；
   · 「不定疯狂」与「潜在疯狂」互斥，同时只能有一个；
   · **不定疯狂 + 其疯狂症随轮次消失 → 潜在疯狂**；
     临时疯狂 + 疯狂症随轮次消失 → 回正常（临时疯狂不产生潜在疯狂）；
   · 潜在疯狂 + 损失任意 SAN(>0) → 立刻回到不定疯狂，并**新生成一条**疯狂症；
   · 治愈按钮 / 成功的精神分析 → 取消 不定疯狂 与 潜在疯狂。

2) 由谁算：`lib/domain/madness_state.dart` + `lib/domain/room_model_actions_sheet.dart`
   （SAN 损失分支 ④「潜在疯狂 → 不定疯狂 + 新症状」，代码注释明确写了这条链
   「不是这里另写一份 if」，即复发走同一条规则出口）。
   老值兼容：`lib/domain/normalize.dart:150` 把老值「不定疯狂（症状消失）」翻译成
   「潜在疯狂」；`room_model_actions_room.dart:41` 同样接受老值。

3) UI 侧只做两件事（都是显示，不含判定）：
   · `lib/ui/card_edit/status_editor.dart:297` 显示「（转入『潜在疯狂』：再损失任意
     SAN 会立即复发）」提示条；
   · `lib/ui/room/sheets/sheet_kp_directives.dart:45` 治愈文案同时覆盖「不定疯狂 /
     潜在疯狂」，避免 KP 以为潜在疯狂治不了。
   · `lib/ui/status_ops.dart:153` 注释记录「不定疯狂 / 潜在疯狂互斥」的 P8 口径。

4) 链路核实结果（全量 2106 内实际跑到，非纸面）：
   · test/p8_madness_state_test.dart（33 处引用，状态机逐分支）
   · test/p10_t3_broadcast_potential_png_test.dart（14 处，含「潜在疯狂」广播口径）
   · test/p10_t3b_rule_diff_test.dart（8 处）
   · test/p10_t6_room_fixes_test.dart（9 处）
   · test/p11_lifecycle_test.dart（13 处，续玩/重连后不残留幽灵态）
   · test/p8_notice_slot_test.dart（3 处）/ test/qa_p10_4_verify_test.dart（9 处）
   → 全部通过。即：**判定在后台（domain）完成，UI 只呈现**，与用户预期一致；
     没有「UI 自己判一次」的第二套口径（那才会漂移）。
