二、本期补的缺口：T-64 confirm=kp 的端到端闭环
----------------------------------------------------------------
【问题】P4 只验了 domain 侧「state.edit.self 入 pending 队列」；
       KP 面板也有待确认区；但「KP 点同意 → 数值真生效」这条
       UI 端到端链路**没有测试**。

【为什么它是缺口而非小事】Q-P5-3 的文案是「数值：需 KP 同意后才能生效」。
       如果同意后不生效，UI 就是在骗用户（K7 违规）；
       如果未同意就生效，confirm=kp 则形同虚设。两个方向都必须有断言。

【核查结论：链路本身是通的】
       intent(confirm) → confirmPending(seat, p)
         · 仅 KP 可调（seat != kHostSeat 直接拒）
         · 按 op + by 定位待办
         · agree=true → applyAction(entry['by'], entry['p'])
           ↑ 用**发起者座位**重放，所以 stateSelf 拿到正确的 seat
       且 UI 发的 payload 不带 seat 是对的 —— 座位由权威端从发起者身份推导，
       与 P4 测试里那个冗余的 'seat' 字段无冲突。

【新增测试】test/room_ui_confirm_flow_test.dart（3 例，全绿）
       1. 玩家提交 HP=7 → 入队且权威态不变 → KP 点「确认」→ HP 真变 7
          （同时断言待办被消费、确认按钮消失）
       2. KP 点「取消」→ 数值不变，待办同样被消费
       3. 旁观者强行打开同一弹层 → 队列恒空（hostRead == null）、
