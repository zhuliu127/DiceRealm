零、Round 2 改了什么（先读这一节，再看下面的第一批原文）
---------------------------------------------------------------
QA 独立回归报告 `qa_p6_close_report.md` §4（已读原文取证）把我上报的两条
「已知限制」判定为**功能性 bug**，主理人裁决采纳，Round 2 打回修复，硬上限最后一轮。

两条是**同一个错误抽象的两面**：`FeedFlashTracker.check()` 用「全局 evt.seq
的差值」同时去推断两件语义事件 ——「是不是断线补拉」和「是不是一次涌入太多」。
但 `lib/domain/room_model_reduce.dart` 给 chats / logs / dice 写的 `'seq'` 全是
**全局事件序号**（三类事件共用同一个 `evt.seq`），不是每个 pane 自己的序号：
  · 短断线只漏 1~6 个事件 → 差值太小（QA 复现 10→13），够不到阈值 6，
    补拉回来的一批被当成新消息**误闪**（限制 2 / QA §4.1）；
  · 正常在线、两条聊天之间夹了 7 条记录/骰子 → 差值被放大到 8
    （QA_PROBE_LIMIT3 base=7 now=15 jump=8），新聊天被误判成补拉而**漏闪**
    （限制 3 / QA §4.2）。
靠调阈值或换 seq 口径都只是把出错场景挪位置。第一批把它当「已知限制」写进
第九节第 2/3 条，等于把需求违约转写成设计取舍 —— 这是错的，现予订正。

**正解**：补拉改由**连接层显式信号**告知，`seq` 差判据整个退役。

修法（5 个生产文件 + 1 个测试投帧口，细节见第五节与第十节）：
  1. `lib/ui/room/room_session.dart`：新增 `int get syncEpoch => 0;`
     带默认实现 —— 本机会话（LocalLoopback / Hosting）没有重连概念，恒 0，
     既有实现零改动。
  2. `lib/net/lan_client.dart`：新增 `int syncEpoch = 0;`，在 `_deliver()` 里
     `client.receive(msg)` 返回 `ReceiveResult`、`result.kind == 'sync'`
     （即 P4 客户端**应用完成**一份全量 sync、state 已被整体替换）后自增。
     三条补拉路径 —— `_scheduleRetry()` 自动重连补拉、`_deliver()` gap 自愈补拉、
     `RemoteSession.pullSync()` 显式补拉 —— 最终都由服务端回的**同一份全量
     sync 信封**汇入这一处；不猜 seq、不把 `resync→connected` 当成「已应用」、
     不新增 notify，复用 `_deliver()` 末尾已有的 `onChange?.call()`。
     另加 `@visibleForTesting void deliverForTest(Map<String, Object?> msg)`，
     让测试能投合法应用层信封走真实链路，不必起真 socket、不碰传输帧协议。
  3. `lib/ui/room/room_session_remote.dart`：
     `@override int get syncEpoch => _client.syncEpoch;`，把世代透出给 UI。
     重连时 RemoteSession 对象不换（座位不变 → client 不重建，只 notify），
     所以 `identical(session, old)` 感知不到补拉，世代是唯一可靠信号。
  4. `lib/ui/room/room_feed_flash.dart`：删掉 `floodThreshold` 字段、构造参数
     与 `if (lastSeq - prev > floodThreshold) return false;`。
     保留三条纯数据守卫：首次登记基线返回 null、`lastSeq <= prev` 不闪、
     `lastSeat.isNotEmpty && lastSeat == mySeat` 不闪。判据不再越界猜批次语义。
  5. `lib/ui/room/widgets/gp_feeds.dart`：`_GpFeedsState` 加 `_boundEpoch`；
     `build()` 里 `if (!identical(scope.session, _boundSession) || epoch != _boundEpoch)`
     → `reset()` + 清 `_checkedSeq`/`_flash` + 更新 `_boundEpoch`。
     ★ 顺序要点：清 `_checkedSeq = -1` 让**本次** build 仍重新走进 `_deriveFlash()`
     登记首屏基线，否则短路会跳过登记，补拉后第一条真消息反被当成首次而漏闪。
     `const GpFeeds(...)` 与 `room_game_page.dart` 两个 const 调用一行未改。

判据**唯一来源**仍是 `FeedFlashTracker.check()`；`syncEpoch` 只是「补拉已发生」
的连接层事实，不是第二条「该不该闪」的判断。

以下第一 ~ 四节、第六节保留第一批原文（作为 Round 1 记录），凡与 Round 2 冲突
的数字 / 措辞均已就地订正并标注。

【限制 2 · 短断线重连补拉误闪】 —— ✅ 已修复
  原症状：短断线只漏 1~6 个事件，补拉后聊天列末条 seq 从 10→13（≤6）、
    又是别人发的，`check()` 返回 true → 误闪。真机 P0 清单第 10 步
    （飞行模式 10 秒）必然走到。
  为什么原抽象错了：`reset()` 只接「session 对象替换」，但 P6 重连时
    `RemoteSession` 对象自始至终不换（座位不变 → `client` 不重建，
    `onChange` 只 `notifyListeners()`）。第一批于是想用「seq 差值 > 6」
    去**间接猜**补拉 —— 差值 3 猜不到，短断线必漏。补拉是**连接层事实**，
    不是可以从展示数据的序号差里推出来的东西。
  修法：连接层在「一份全量 sync **应用完成**」时把 `syncEpoch` +1，
    `RemoteSession` 透出，`GpFeeds` 观察到世代变化即 `reset()`。
    三条补拉路径（自动重连 / gap 自愈 / 显式 pullSync）都汇入 `_deliver()`
    里 `result.kind == 'sync'` 这一处，不新增 notify。
  验收：短断线漏 1 / 2 / 3 / 4 / 5 / 6 个事件、重连补拉后
    聊天列 + 记录列都不出现角标（6 组参数化回归）。
  反向：把 epoch 信号改成恒返回 0 → `+10 -7`，7 条限制 2 用例全红。

【限制 3 · 全局 seq 与 pane 局部序列错配漏闪】 —— ✅ 已修复
  原症状：正常在线，「2 条历史聊天 → 7 条公开骰 → 1 条别人新聊天」，
    聊天列末条 seq 跳跃 8（QA_PROBE_LIMIT3 base=7 now=15 jump=8），
    `GpFeedsKeys.flash(FeedPane.chat)` `findsNothing`（PRD 期望出现角标）。
  为什么原抽象错了：阈值 6 隐含的是「**每列自己的新增条数**」，但
    `reduceRoomState` 给 chats / logs / dice 写的 `'seq'` 都是**全局事件序号**，
    `collectChats` / `collectFeeds` 又原样取它。别列交错会把差值放大，
    于是正常在线的新消息被误判成「补拉」。旧版 `room-ui.js:3748
    feedFlashCheck` 本来只有「首次登记基线 + 不是自己发的」两条规则，
    没有 flood 抑制 —— 这条阈值是第一批从**操作播报**误搬过来的功能退化。
    而且它同时承担「猜补拉」和「猜涌入太多」两个语义，本身就是错抽象。
  修法：`FeedFlashTracker.check()` 删除阈值字段、构造参数与 seq 差规则，
    只回答「有没有新条目 / 是不是自己发的」；补拉不闪完全交给连接层
    `syncEpoch` 触发的 `reset()`。判据不再读任何批次信息。
  验收：两列交错（7 公开骰夹在中间）时 chat 角标 `findsOneWidget`，
    且 `jump > 6` 有前置断言保证确实覆盖旧判据会误杀的场景；
    另有一条「只来记录、不来聊天 → chat 不闪」守两列独立。
  反向：临时把 `if (lastSeq - prev > 6) return false;` 加回 → `+35 -6`，
    3 条如实重写的纯逻辑用例 + 2 条接线 + 1 条限制 3 用例全红。
