一、两个文件的规模与职责
----------------------------------------------------------------
room-net.js   78,837 B（≈1670 行）  传输层：HTTP + WebSocket
room-lan.js    6,458 B（≈171 行）   局域网门面：只做「地址从哪来」

**room-lan.js 的核心洞察（直接决定 P6 的架构走向）**
  它的注释原话：
    「局域网不是「另一条链路」，只是「地址从哪来的问题」。」
  具体做法：把外壳返回的 {ok, base, ip, port} 写进全局 ROOM_SERVER_BASE，
  于是 room-net.js 的 base() 立刻可用 —— **传输层一行都不用改**。

  对照 P5：`_p5_prd.md` §9.4 已按这个思路留了 `RoomSession` 端口 +
  `LocalLoopback` 同进程实现。P6 要做的是把这个端口的**远端实现**补上，
  而不是重写 UI 那套。

二、room-lan.js 对外面（10 个）
----------------------------------------------------------------
available()   本环境能否开局域网房（有外壳 + 有局域网地址）
isApp()       是否跑在安卓外壳里（只问有没有桥）
ip()          本机局域网 IP
start()       开房 → {ok, base, ip, port, wifi}
stop()        关房 + 清注入地址
injected()    当前注入的地址（空串 = 不在局域网模式）
running()     桥报告的服务是否在跑
discover(ms)  UDP 广播发现，默认 1600ms，兜底 +600ms
asRoomEntry() 把发现结果转成「房间目录」同一形状（界面复用同一段渲染）
DISCOVER_PORT 4210

**三个容易漏的细节（旧版踩过的坑，P6 别重犯）**
1. `wifi: false` 表示外壳把 base 退化成 `http://127.0.0.1:4211` ——
   那间房只有自己能进，邀请链接对同伴是死路。
   ⇒ **必须在建房之前就提示**，不能等用户拿两台手机试半天。
2. discover 的超时要在**调用方**再套一层：外壳的桥调用可能因权限被拒
   而静默失败、回调永不到来，界面会一直转圈。
3. injected() 必须单独存在：光看 running() 不够 ——
   桥可能说没跑、地址却还留着（上次异常退出）。

四、移植到 Dart 的关键差异（架构师要先回答的）
----------------------------------------------------------------
旧版：WebView + AndroidBridge（Java 外壳开端口跑 HTTP 服务 + UDP 广播）
Dart：**能直接开 socket，外壳可以整个不要了**
  · HTTP 服务：dart:io HttpServer 直接绑端口
  · WebSocket ：同端口 upgrade，或独立端口
  · UDP 发现  ：RawDatagramSocket 广播/监听 4210
⇒ room-lan.js 那层「委托给外壳」的门面在 Dart 里**没有存在必要**，
  它的三个坑（wifi 退化 / discover 静默失败 / injected 残留）会变成
  纯 Dart 里的等价问题，仍需处理，但不再需要桥接。

**红线（P4/P5 已确立，P6 必须守）**
K3：中继**禁止**直接序列化 `LogRecord.toWireJson()`（含明文 p），
    否则 Q1 修正在补拉路径被绕开。
    ⇒ 中继只能转发 `plan()` 产出的已裁剪 SendPlan / 已脱敏信封。
