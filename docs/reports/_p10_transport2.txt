## 一、做了什么（对用户两条点名需求）

### 需求 1：「显示头像缩略图让游戏中的玩家栏里面也显示头像」

**真因**（第 1 期遗留）：头像文件落在**本机私有目录**（`avatars/<cardId>.png`），
角色卡里只存**相对路径**；房间协议不传二进制。于是：
- 绑卡上报时 `sheet.avatar` 是一条本机相对路径 `avatars/c1.png`；
- domain 的 `sanitizeSheet` 只收 `data:image/(png|jpe?g|webp);base64,` 且 ≤20000 → **判成 `''`**；
- 远端那台设备既没有文件、也没有 dataURI → 玩家栏永远退化成首字圆点。

**本批做法**（严格照老 APP v2.13.7 口径，不另设计）：

1. **新增 `lib/repo/avatar_thumb.dart`** —— 头像缩略图生成（纯 `dart:ui`）：
   - 解码 → **短边居中裁正方形**（`side = min(w,h)`，`sx=(w-side)/2`）→ 缩到 **64×64** → 编码
   - 与老 APP 逐行同口径，只有编码格式不同（见「关键决策」）
   - 输入：本机相对路径（读 `avatarStore` 的绝对文件）**或**已是 `data:image/*;base64,` 的值
   - 无头像 / 文件不存在 / 解码失败 / 超限 → **空串**（绝不抛、绝不返回半截）
   - 体积超 20000 → 按 `64 → 48 → 32` 阶梯降尺寸
2. **新增 `lib/domain/avatar_uri.dart`** —— 头像 dataURI 的**纯字符串判据**
   （`^data:image/(png|jpe?g|webp);base64,` + `length ≤ 20000`，逐字对齐老 APP
   `room-model.js:7306`）+ 同步 base64 解码。放 domain 是因为**视图层
   `feed_view.dart` 也要用同一份规则**，但它不该被引擎依赖污染。
3. **绑卡上报带缩略图**：`card_sheet_payload.dart` 新增
   `cardToRoomSheetForReport(card)` —— 先把 `card.raw.avatar` 压成缩略 dataURI，
   再放进 `sheet.avatar`；**没有就 `remove('avatar')`（键不存在，不是空串）**，
   完全复刻老 APP `reportSheet` 的 `delete sum.avatar`。
   `sheet_bind_char.dart` 的「绑定 / 清空」改成 `await` 这条路径（生成完才发 `INTENT.CHAR`，
   顺序同老 APP 的「在回调里才 sendIntent」）。
4. **`AvatarThumb` 支持 dataURI**（`lib/ui/widgets/avatar_picker.dart`）：三层优先级
   - ① 本机相对路径 → `FileImage`（**原图高清，512px，优先**）
   - ② `data:image/*;base64,` → `MemoryImage`（**同步解码**，列表几十行也不挂 Future）
   - ③ 都没有 / 解码失败 → `AvatarDot` 首字圆点
5. **玩家栏（用户点名）**：`memberAvatarRel` → 新增 `memberAvatarValue`，并在
   `gp_pl_mates.dart`（玩家侧队友栏）+ `gp_kp_players.dart`（KP 侧玩家栏）切过去。
   取数顺序：**本机文件真的存在 → 走文件；否则用 `sheet.avatar` 的 dataURI；都没有才圆点**。
6. **聊天 / 公开记录条目头像**（对齐老 APP `feedAvatarForSeat` + `feedAvatar`）：
   `FeedItem` 新增 `avatar` 字段，`collectFeeds`/`collectChats` 按 `seat` 反查成员
   `sheet.avatar`（只认合规 dataURI，超 20000 置空）；`FeedRow` 左侧渲染 18px 缩略图
   （没有头像就**不渲染整块**，不留空位）。
7. **只给你看（私密）条目头像**：`GpPrivatesRow` 左侧画 **KP 头像**
   （私密信息由权威端下发；私密行只有 `{seq,title,text,at,kind}` 五键，故意不带 seat，
   所以按 `kHostSeat` 反查成员表；拿不到就是空串 → 不渲染，绝不虚构发送者）。

## 三、关键决策（含如实说明）

### 决策 1：PNG vs JPEG —— 体积实测

- **硬约束**：`ui.Image.toByteData()` 只支持 `rawRgba` / `png`，**没有 JPEG 编码器**；
  `pubspec.yaml` 本批不许改（不能引 `image` 包）。所以只能用 PNG。
- **实测**（本机，`p10_t2_avatar_test.dart` 打印）：
  - 300×300 彩色噪声图 → 64px **PNG base64 = 7,102 字符**（约 5.2KB 二进制）
  - 纯色 / 两色图 → 200–600 字符
  - 结论：**远低于老 APP 的 20000 上限**，广播体积安全（老 APP JPEG 0.72 约 2-4KB，
    本批 PNG 同类图约 5-7KB，**约 1.5-2 倍**，但仍只有上限的 1/3 以内）。
- 若某张图仍超 20000 → 自动降到 48 → 32（有确定性用例：先量 64/48 的真实体积，
  再把上限卡在两者之间，断言真的降到 48）。
- **不假装一样**：这是与老 APP 的**唯一实质差异**，已写进代码头注释与本报告。

### 决策 2：C2 与 tempCommit 的取舍 —— 以 tempCommit 为唯一触发源

团队口径倾向「tempCommit 为唯一触发源，C2 原有回合号去重逻辑复用作幂等保护」，**照办**：

- **保留**：`RoomCardSaver` 的 `_busy` 重入保护、`_lastAutoRound` 幂等、失败静默、
  `canSave` / `saveNow` 手动保存（C1）。
- **替换**：触发判据从「`meta.round` 变了」→ 「`session.lastTempCommitRound` 变了」。
  理由（老 APP 注释原文）：天/周恢复会经 `EVT.STATE` 改临时卡（重伤每周回血），
  若一看到回合号变就落库，玩家会把**恢复前**的旧值覆盖回原卡。
- **为什么不会两套机制打架**：判据只剩一条来源（TEMP_COMMIT），`_lastAutoRound`
  只做幂等键（存的是 TEMP_COMMIT 的 round）。同一批里没有第二个写入口。
- **Flutter 侧没有「localStorage 临时卡」这个东西**（老 APP 的 `KEY_TEMP_PREFIX + roomCode + '.' + charId`）：
  房间 state 本身就是唯一暂存面，`roomCardPatchOf` 从它取值 → 覆盖原卡，
  与老 APP 的 `commitTempCard` **语义等价且天然幂等**。
  所以老 APP 的 roomCode 隔离在 Flutter 侧是**结构性成立**的（每个会话只看自己那份 state），
  本批用「两间房并存、别房推进回合、本房不落库」的用例把它钉死。

### 决策 3：缩略图生成放 repo、判据放 domain

- `lib/repo/avatar_thumb.dart`：用引擎画布（解码 / canvas / PNG 编码）→ repo。
- `lib/domain/avatar_uri.dart`：纯字符串判据 + 同步 base64 → domain（视图层要用同一份规则）。
- 红线：`lib/domain/**` 零 Flutter / 零 IO / 零 UI —— 已用 `domain_purity_test` + P5 门禁双验。

### 决策 4：私密栏头像的来源

老 APP 的私密卡（`fillPrivCard`）**本来就没有头像**；本批按团队任务书补上，
做法是**画 KP 头像**（私密信息由权威端下发），绝不虚构发送者。
若将来私密行需要真实发送者，得在 `reduce` 的 PRIVATE 分支加 `seat` —— 那会改存档形状，
本批**没有**动（避免砸 P4 oracle 夹具）。

## 四、自己踩的坑（给后来人）

1. **domain 注释里的字面量也会被门禁扫到**。`lib/domain/avatar_uri.dart` 头注释里写了
   `package:flutter` / `dart:ui` / `dart:io` 三个词（只是说明「零依赖」），
   直接让 `domain_purity_test` 与 `qa_p5_ui.js` 判据 07 变红。
   → 注释里改成「Flutter 框架包 / 引擎 / 文件系统」这类描述。
2. **`setUpAll` 里造图**。`testWidgets` 跑在 fake-async 区域，`picture.toImage()` 的
   Future 永不完成。头像素材必须在 `setUpAll`（fake-async 之外）生成一次再复用；
   同理 widget 用例里的文件写盘一律用**同步** `writeAsBytesSync`。
3. **`sentLog` 的形状是 `{to, msg:{k,t,p}}`**，不是信封本身 —— 第一版诊断函数在顶层找
   `k`，于是「批次里有 round」永远判成 false，白跑一轮。
4. **`round.next` 在统一出口之后还会追加一条系统播报**（`EVT.LOG`），
   所以 TEMP_COMMIT **不是整批计划的最后一条**（老 APP 也一样）。
   正确断言是「它排在 round 与所有 state/dice 之后，且之后只有 log」。
5. **`sheet.damage` 之后那一回合会 +1 HP**（1 回合 = 1 天）。第一版用例拿「打伤后的 HP」
   去比「存下去的 HP」，差了 1 —— 但这个差值恰好证明了顺序正确，
   于是把用例改成「存下去的必须等于**恢复后**的值」，反而更有力。
