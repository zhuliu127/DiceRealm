二、契约隔离策略（照抄上一批 ai_caps.dart 的双路径套路）
---------------------------------------------------------------
问题：旧版 core/share.js#buildPayload 的 data 里没有规则字段；P3 两处
      冻结逐字节 oracle（qa_p3_h2_h3_test.dart:294-298 / :305-309、
      qa_p3_final_gate_test.dart:350-356）抓的就是旧版请求体，冻结 fixture
      的 cards 也没有 ruleSystemId。生产要真发规则字段，两者必然冲突。

策略：`legacySharePayloadForOracle`（默认 false）直接作用在
      **ShareClient.create() 实际调用的同一个 buildSharePayload** 上：
        false（生产 / 全部其它测试）→ data 追加 ruleSystemId + ruleShortName；
        true （仅两处 P3 预言机 setUp）→ 一个字段都不加，逐字节回到旧版。
      探针各自 setUp 快照、tearDown 还原，文件间 isolate 隔离，串跑并跑都不串味。
      **没有**另写 buildSharePayloadLegacy 给测试用 —— 那会把 oracle 降级成
      测一个没人调用的死函数。

自证伪（p7_share_badge_test.dart 第 ④ 组，双向）：
      · 开关 true  → jsonEncode(buildSharePayload(captures[0] 的卡)) 与冻结
                     captures[0]['body'] **逐字节相等**；
      · 开关 false → 与冻结 body **不相等**，且 prodBody 含 "ruleSystemId"；
      · 把两个新字段从 prodData 摘掉后，jsonEncode 与 legacyData **逐字节相等**，
        证明差异只来自规则字段，旧版其它字段一个字节都没被改坏。
      → H3/G3 若去掉隔离会真红，不是摆设。

wire 级自证（第 ③ 组）：起真实 FakeServer，让 ShareClient.create() 真发一次
      HTTP，解 server.requests.single.body 断言 data 里真有规则字段；
      不是只测纯函数。
      ★ 实现细节：本文件同时含 testWidgets，flutter_test 在**注册**
        testWidgets 时就设了 HttpOverrides.global = _MockHttpOverrides（裸
        HttpClient 一律 400）。故真实 HTTP 用例跑在
        `HttpOverrides.runWithHttpOverrides(..., _RealHttpOverrides())`
        的干净 zone 里，空子类继承基类 createHttpClient 的默认实现（构造真
        _HttpClient）。这是 qa_p3_* 两文件「刻意不含 testWidgets」的同一原因，
        没有靠改环境或放松断言绕过去。

六、已知边界（如实列出，不藏）
---------------------------------------------------------------
1. 服务端只读页的回退**只在 render_card**：本机 ShareRecord 对老记录如实
   留空并显示「未标注规则」，两者语义有意不同（一个面向看链接的人、
   一个面向卡主人），不是 bug。旧链接点「更新为当前版本」会重新 create
   一条新 id，服务端才有规则字段；旧 id 本身不会被回填。
2. 规则字段只加在 POST /api/cards 的 data 层，靠服务端「整包 pack(data)
   不校验白名单」自动透传。若将来部署方把 coc_share_server.py 换成别的实现
   或加了字段白名单，徽标会退回 COC 7th（不会报错，但新规则名丢失）。
3. 占位规则（dnd5e / custom）在 effectiveId 口径下收敛回 coc7，所以本批
   线上永远只会显示 COC 7th / coc7；服务端已支持任意 ruleShortName 原样
   渲染（Python 第 5 组证明），但真正多规则要等规则层开放新规则之后。
4. 未启动模拟器 / 未做真机跨设备打开链接验证，第 8 条真机验收由 QA 补。
   本批自动化只覆盖到「请求体真发字段」+「render_card 纯函数渲染」，
   没有跑端到端 HTTP GET /s/<id> 与浏览器 CSS 呈现。
5. APK 仍是 debug 签名，可侧载不可上架（与上一批一致）。
6. 本批 APK 字节数与上一批恰为同一值（60,635,735），但 SHA256 不同且
   AOT 内查到本批新增的 4 个标识字符串，确认不是「跳过 AOT 的坏包」；
   libapp.so 三个 ABI 大小与上一批相同，属 AOT 快照长度对齐后的正常现象。
